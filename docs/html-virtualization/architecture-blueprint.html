The prune

The old backlog wasn't wrong so much as sized for a different company. It ranked nine infrastructure topics and queued seven of them — provider selection, environment matrices, observability stacks, Redis cache keys — ahead of the first line of application code. For a solo MVP with zero users that ordering inverts the actual risk: what most likely kills Grains is not an unpooled connection, it is nine months of infrastructure decisions and no product.

01

Stack architecture

Decided
The shape, in one paragraph

One Next.js application. App Router, Server Components for reads, Server Actions for writes, Drizzle over Postgres. No separate backend service, no wire contract, no second language, one deploy. One discipline survives from the old hexagonal plan: SQL exists only in lib/queries/ — pages, actions and handlers call those functions and never write SQL inline.

Decision ledger

01One Next.js application, not two deployablesDecided

Decision — App Router. Server Components read the database directly; Server Actions own every write; Route Handlers exist only for what the browser fetches after load. Rejected: the previously-resolved Go service + Next.js frontend over an OpenAPI contract.

Rationale:

  • The hardest open question disappears. The old §5's central problem was how a Go service verifies a session the frontend's auth provider created. In one process, auth() returns the session. The decision evaporates rather than getting answered.
  • Agent-assisted development is the stated primary mode. Adding an endpoint went: edit openapi.yaml → regenerate → lab.go → repository.go → postgres.go → service.go → http.go → regenerate the client. It now goes: add a query function, call it. Fewer files per task is worth more to an agent than uniform files per task.
  • The old objection to serverless does not apply here. §1.3 ruled out per-request functions because 50 concurrent invocations means 50 database connections. Supabase's transaction pooler is built for exactly that. The other half of §1.3 — region co-location — was the expensive-to-reverse half, and it is kept in full.

Costs knowingly accepted:

  • The developer wanted to write Go, and this takes that away. That was the honest, primary and legitimate reason the old §1 chose a Go service, and nothing here refutes it — preferences about what you enjoy building are load-bearing on a solo side project.
  • Vendor gravity toward Vercel. RSC and Server Actions run elsewhere, but not without work.
  • No language boundary means no structural guard against business logic leaking into components — mitigated only by the lib/queries/ rule, and by keeping updateLab a single transactional function.
Override note — wanting the Go backend anyway is a sufficient reason on its own and costs no credibility; it was chosen on preference, and reversing a preference-based decision is free. But take the lean Go shape, not the old one: Go + chi + sqlc, no hexagonal packages, no service layer where there is no logic, no OpenAPI codegen — a hand-written typed lib/api.ts is smaller and more honest at ~20 endpoints with one consumer. Budget a day for JWT verification (shared AUTH_SECRET, HS256, not JWKS). Everything else on this page holds unchanged under either branch.

02SQL lives in one directoryDecided

Decision — lib/queries/*.ts is the only place SQL appears. Pages, Server Actions and Route Handlers all call into it; none of them write SQL inline.

Rationale — This is the one boundary from the hexagonal plan worth keeping. The other four layers were paying for a database swap that a PostGIS-dependent product can never perform, and the third type representation they implied would have run to hundreds of lines of field-copying per entity for no benefit.

lib/db/schema.ts     Drizzle schema — mirrors schema.sql, source of inferred types
lib/queries/         the only place SQL exists: labs.ts films.ts photos.ts books.ts
lib/auth.ts          Auth.js config; auth() returns the session server-side
app/**/page.tsx      Server Components — call lib/queries directly
app/**/actions.ts    Server Actions — all writes
app/api/**/route.ts  the three GET handlers
02

Data layer

Decided
The shape, in one paragraph

PostgreSQL 15 + PostGIS on Supabase, Singapore (ap-southeast-1). Drizzle ORM. Raw SQL migrations. No cache. Supabase wins over Neon on one argument: this is a photo product, so object storage is needed on day one, and picking Neon means a second vendor for storage anyway. Accepted in exchange: weaker branching, and a free tier that pauses a project after seven idle days.

Decision ledger

01Supabase Postgres + PostGIS, via DrizzleDecided

Decision — Drizzle rather than Prisma: schema-as-TypeScript, types inferred rather than generated, and it gets out of the way when a query needs raw SQL — which every geospatial query does. Migrations are raw .sql files applied by drizzle-kit, with PostGIS DDL hand-written.

PostGIS is for correctness, not speed. At tens to low hundreds of labs, haversine over float columns would also run in well under a millisecond. It stays because the usual hand-rolled substitute is a bounding box — which returns a square, so a lab 7km away shows up in a "5km" search — and because hand-written haversine invites an earth-radius constant that differs between the WHERE and the ORDER BY, silently filtering and sorting by different distances. ST_DWithin is one line and correct. Do not cite performance as its justification.

02Same-field edit collisionProposed

Decision — Whole-row optimistic concurrency on labs.version, with per-leaf-path diffs in edit_history. Recorded as proposed rather than decided: cheap to overturn before implementation, but the column has to exist in the first migration, which is the part that cannot be retrofitted cheaply.

Rationale — Slightly pessimistic: two contributors editing genuinely different fields will collide. At this traffic that is approximately never, and the alternative — per-field version vectors — is a large amount of machinery to avoid a conflict dialog nobody will see. Diffs still record individual leaf values (pricing.c41.135.price_thb) rather than field groups, so the history log stays precise.

03

Hosting & auth

Decided
The shape, in one paragraph

Vercel + Supabase, both Singapore. Auth.js v5 with Google. Two environments. Local development connects to the same grains-dev project that Vercel preview deploys use — which deletes docker-compose, deletes "keep PostGIS versions consistent across environments", and deletes a whole class of works-on-my-machine drift. Cost: no offline development, and ~30ms per query from Bangkok.

Not built for MVP

  • No public read API, and no second consumer to justify one.
  • No pagination beyond the edit log and the film gallery.
  • No rate limiting beyond the per-user upload cap.
  • No follow / feed endpoints — deferred post-MVP with the discovery model.
  • No moderation queue; every contribution goes live immediately.

Still open, and the build order

Genuinely open — none of it blocks the first commit

Upload cap value50 as a placeholder. A content decision, not an architecture one.
Catalog rostersBadges, services, supplies and scanner models are seeded in schema.sql as a starting set. They are rows, so changing them is not a migration.
Reverse search → map filterThe schema and /api/labs already support film_stock_id. This is a UI question now.
Orphan Photos on a profileWhere a Photo belonging to no Photobook surfaces on /u/@username. A design question.
Bilingual strategyname_en/name_th are in the schema; the UI-copy approach (next-intl vs. a hand-rolled dictionary) is unresolved and cheap either way.

Build order — a ranking of tickets, not of decisions

  1. Scaffold. create-next-app, Tailwind, shadcn/ui, Drizzle, Auth.js. Two Supabase projects. Deploy an empty page to Vercel on sin1 and confirm the region. Update CLAUDE.md with the real commands in the same commit.
  2. Migration 0001 — schema.sql verbatim, seeds included.
  3. Google sign-in + claimUsername. Everything that writes depends on a user row existing.
  4. Labs read path. /api/labs with ST_DWithin, then /labs/[id]. Seed ten real Bangkok labs by hand — a discovery product is untestable and unlaunchable without real rows, and ten real ones beat two hundred fake ones.
  5. Labs write path. createLab / updateLab, one form in two modes, version check, edit_history. The endpoint with actual invariants — give it the most care and the only tests worth writing early.
  6. Film stocks — catalog, inline add, lab_stock linkage, reverse search.
  7. Photos and Photobooks — the upload flow above, then /u/@username, then Connections. Ship here.
  8. Badges. One table, one toggle, an afternoon.
  9. Sentry, then the pending/ cleanup cron.
